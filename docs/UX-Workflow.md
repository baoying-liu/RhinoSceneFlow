# 用户体验优先：设计、实现与验收

本规范用于 SceneFlow 后续用户功能的开发与审查，覆盖 Rhino 原生 Eto 工具和 Web 工作台。它定义工作方式，不表示现有界面已经全部满足这些要求，也不授权重构无关界面。具体的数据、渲染、生命周期与回归要求仍以 [技术约束](Development-Contracts.md) 为准。

## 1. 按改动规模执行

小修复先沿用已有交互，检查受影响的正常流程和恢复路径；不为改一个标签编造两个方案，也不要求每次新建报告或测试文件。

新工作流、较大的交互变化或新增设置入口，需要比较至少两种可行方案。比较用户要做的动作、信息是否容易找到、误操作后果及恢复成本，不能只比较点击次数或视觉效果。选定方案后，在进度说明或已有任务记录中简短记录理由即可。

如果已有授权足以覆盖合理的实现选择，继续完成工作；不要把这份规范变成反复确认的审批流程。遇到明显更好的体验，主动给出简短建议；涉及无关页面、功能语义或较大范围变更时，先说明范围与影响。

## 2. 开发前：先定义用户任务

主要使用者通常是在 Rhino 中完成建筑、景观设计的专业用户，同时需要兼顾首次使用者的可发现性和熟练用户的操作效率。每次改动仍应明确本次实际使用者与目标。

开发前回答以下问题：

- 用户从哪里开始，当前选中了什么，想得到什么结果？
- 用户必须知道哪些信息，哪些可以用可靠默认值处理？
- 现有哪个工具、列表、面板或快捷键已经能承载这个动作？新增入口是否重复？
- 这个动作改变原图、生成结果、生成配置、空间标注，还是仅改变显示？
- 用户最容易选错什么、误解什么？取消、撤销、重试或恢复后应保留什么？

较大改动的轻量记录可以使用：

```text
用户与目标：
起点、选择和预期结果：
方案 A / B：关键步骤、可发现性、误操作与恢复成本
选择及理由：
复用或替换的现有入口：
本次修改范围：
验收路径与主要风险：
```

没有额外设计需要的小修复，可以在任务说明中用一两句话覆盖这些要点。

## 3. 实现时：保持操作可预测

### 入口与布局

- 每个工作阶段有清晰的主要操作，次要操作与低频管理功能有明确层级。
- 同一设置有一个主要管理入口；其他位置可以是快捷入口，但必须操作同一份状态，避免独立副本和相反含义。
- 频繁操作容易找到且操作迅速。高级设置按需展开，不能把完成主要任务必需的内容藏进高级区。
- 优先使用上下文操作、行内编辑和现有控件。弹窗用于确有必要的输入、检查或风险说明，不能成为每次点击的中转站。
- Rhino 工具遵循原生选择、停靠与命令习惯；画布遵循已有的平移、缩放、拖动和标注习惯。两端共享操作含义，不强求控件外观完全相同。

### 上下文、选择与快捷键

- 刷新、参数修改、保存和返回编辑器时，保留仍有效的目标、选择、输入焦点、滚动位置、视口和对比位置。
- 自动定位应符合现有开关及明确动作；单击选择不能无故改变缩放或打断正在做的事。
- 列表、画布、PhotoCraft 与检查器按稳定 ID 对应。同一实体的编辑共享数据；列表顺序、画布布局和各自折叠状态按已有约定保持独立。
- 不用新增快捷键覆盖宿主既有行为。文字输入、中文输入法组合输入、剪贴板和编辑器自己的撤销应获得正确的事件范围。
- 快捷键补充可见入口，不能成为发现某项功能的唯一方式。

### 反馈与恢复

- 用户应知道操作是否已接收、作用于谁、是否仍在运行，以及完成或失败的原因。
- 进度必须来自真实任务状态；没有可靠百分比时显示阶段与活动状态，不编造进度。
- 失败提示说明如何修正或继续，并保留可恢复的描述、参数、选择和已有结果。避免只有“失败”或静默无变化。
- 可逆编辑提供与现有模型一致的撤销／重做；取消运行任务、放弃配置修改、恢复默认和切换图片备份不是同一个动作。
- 恢复有实际限制时明确说明，例如已执行的生成调用不能靠撤销收回，已完成步骤不能假称整批回滚。
- 默认值有依据，允许调整和恢复。自动化重复操作时保留用户明确设置，不静默覆盖自定义值。
- 显示语言、标签和单位表达保持一致；用户描述、文件名、资产名称与植物拉丁学名不随语言切换被改写。

## 4. 状态表达的一致性

以下是设计和验收时必须分清的含义；具体字段、适用对象和权限以技术约束为准，不能由本表推导新的后台行为。

| 概念 | 用户需要理解的内容 | 应避免的混淆 |
|---|---|---|
| 显示／隐藏 | 是否在当前界面可见 | 隐藏不等于停用 AI，也不等于删除 |
| AI 启用／停用 | 下次生成是否考虑该项 | 显示出来不代表一定参与生成 |
| 内容锁定 | 哪些内容可编辑，如何解锁 | 锁定不能让仍允许的查看、选择或边界操作失效 |
| 自动保存 | 描述、参数或布局已经持久化 | 保存配置不代表生成结果已经更新 |
| 待生成／待更新 | 哪些修改尚未用于生成 | 黄色状态不能只靠颜色表达，也不能把选择变化误标为修改 |
| 上游输入变化 | 哪个输入版本变了，下次会使用什么 | 不静默替换历史对比输入；紫色与待编辑状态含义不同 |
| 创建子级／同级 | 建立什么来源关系的草稿 | 创建草稿与实际调用生图分开，白板不冒充 AI 结果 |
| 更新／生成 | 实际输入、作用目标及是否开始模型调用 | 不让用户误以为是在当前结果上改，实际却使用另一个输入 |
| 编辑撤销／结果备份 | 可以恢复哪一类改动 | 配置撤销不承诺自动恢复旧图片，图片备份保持不可变 |

颜色之外还要有文字、图标、名称或说明。关系连线、标注箭头、选中框、考虑框和图片像素边界需要容易区分。

## 5. 实现后：验证完整的受影响流程

先从用户的起点走到可理解的结果，再验证常见误操作和恢复。按风险选择已有回归、原厂 MCP、文件像素检查及隔离的真实浏览器测试，不要求每次新增测试文件；后台成功响应不能替代对实际交互的验证。

| 检查范围 | 需要观察的问题 |
|---|---|
| 正常使用 | 用户能否找到入口，目标是否正确，结果与按钮含义是否一致？ |
| 空状态 | 无选择、无素材、无图片或无匹配结果时，是否说明下一步？ |
| 加载与运行 | 重复点击、切换目标、返回页面时，是否有清晰反馈和正确的任务归属？ |
| 失败与恢复 | 无效输入、资源缺失、过期会话或保存冲突时，能否修正、重试并保留工作？ |
| 成功状态 | 用户能否看出具体完成了什么，下一步是否清楚？ |
| 可逆编辑 | 撤销／重做、取消和恢复是否针对正确对象，是否有残留或误删？ |
| 上下文 | 选择、焦点、滚动、视口、对比拖杆是否无故跳动或丢失？ |
| 界面条件 | 在实际窄侧栏、长名称、多项内容和适用语言下，常用操作是否仍可访问？ |

只检查本功能适用的状态；较大流程变化再覆盖跨工具路径。常用端到端路径包括：

- 材质：选择物件 → 找到或生成材质 → 确定应用范围 → 必要的真实尺寸 UV 准备 → 应用 → 换选物件再次操作。
- 种植：选取植物 → 配置组合 → 放置或散布 → 找到 Plants Group → 编辑单株 → 退出并继续整体操作。
- 导出：选择 Named Views → 检查预览与尺寸 → 配置通道、分组与叠放 → 导出 → 检查文件、重名处理及取消结果。
- AI 后期：导入 → 确认来源 → 创建草稿 → 调参／标注／放入参考 → PhotoCraft 编辑与返回 → 检查本次输入 → 生成 → 对比 → 继续修改或高清输出 → 导出。

使用 Hillside 等案例时优先采用独立副本，保护用户原始数据。优先 MCP 与无系统鼠标的验证方式；真实模型调用仅在验证确有需要且已获任务授权时进行。区分模拟任务、离线重放、实际浏览器和真实 AI 生成证据。

## 6. 发现问题后的处理

先记录具体触发条件、用户感受、预期与实际行为，避免笼统地写“体验不好”。可以复用已有任务、审计或验证文档，不建立强制的新工单流程。

优先处理错误目标、数据损失、无法恢复、任务无法完成和来源不明等问题；随后处理重复入口、上下文跳变、难发现或冗余操作；最后再处理不影响任务的视觉统一。

对于明显更好的交互，简短说明“当前阻碍 → 建议 → 对用户的收益 → 修改范围”。在已有授权内完成相关改进；无关重设计作为建议保留。

交付时说明改了什么、为什么、如何验证及尚存限制。不要把一项流程测试通过描述成整个产品完成 UX 审计。既有 [AI Studio 审计](AI-Studio-Workflow-Audit-2026-11-09.md)、[任务流程](Task-Workflow-0221.md) 与 [PhotoCraft 图层说明](PhotoCraft-Layers-0224.md) 是可复用的背景和证据，不是本次重新执行过的测试。
